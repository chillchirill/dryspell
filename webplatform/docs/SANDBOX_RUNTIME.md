# Sandbox simulation runtime

The standalone sandbox runs the surface-grid-1.3.0 engine in a dedicated browser Web Worker. It imports no database, HTTP server, map library, filesystem or provider adapter. The future geographic workspace can supply the same `Scenario` and `EnvironmentSnapshot` objects without replacing the numerical engine. The current combustion and source-driven observation stage is specified in [FUEL_PARAMETER_MANIFEST.md](FUEL_PARAMETER_MANIFEST.md); the complete research V2 model remains a staged migration.

## Input and numerical contract

`packages/contracts/src/sandbox.ts` defines the `sandbox-v4` command/event protocol. Each load has a strictly newer nonnegative generation; other commands must match the currently loaded generation. The UI should terminate the previous worker to cancel initial synchronous terrain preparation. Subsequent replay reconstruction uses `prepareReadings` for hidden ticks and `prepareFrame` for the displayed target, with bounded fixed-step budgets and yields between batches. A batch checks elapsed time between calls; frame assembly and a single numerical tick cannot themselves be interrupted. Final preparation can consume up to twelve further ticks, including delayed source-state reconstruction.

The sandbox accepts at most 40,000 cells and 500 sensors; thirty is the default workload, not a limit. Duration is user-selected positive hours, converted by the shared contract to safe integer five-second ticks within the representable UTC date range. There is no fixed six-hour duration cap. Existing thirty-minute and six-hour scenarios retain their duration and remain valid. The engine honors the supplied duration and never silently extends a saved scenario. It requires five-second outputs and checkpoints on five-second boundaries. Sensor capabilities may be a unique subset of their declared profile; enabled sensors require at least one channel, while disabled sensors may have none. Undeclared channels remain invalid. Weather samples must be finite, ordered, cover time zero through the full run, and have `validAt` equal to the scenario start time. A missing or misaligned weather snapshot is an error; the worker does not fetch replacement weather or silently extrapolate. The provider adapter may explicitly append a labeled constant-weather tail beyond its available forecast; that assumption belongs to the frozen snapshot's provenance and must remain visible in the UI.

The coordinator supplies an Open-Meteo snapshot before running. That snapshot is frozen with the terrain and scenario in `createSimulationSession`. The session clones and recursively freezes inputs once, then retains private arrival times and sensor checkpoints. It avoids repeatedly serializing the 40,000-cell environment for cache lookup, while keeping the existing server `simulateFrame`, checkpoint, restore and replay APIs intact. Editing requires a new revision/load; changing display layers does not enter these inputs.

SHA-256 uses `@noble/hashes` synchronously, with UTF-8 input and explicit little-endian extraction of the first four bytes for seeded sensor noise. Tests compare the bytes, hex and little-endian integer against Node crypto. The engine version remains unchanged because this portability change preserves numerical inputs, noise and frame/checkpoint checksums.

## Time and playback

- Run advances exactly five simulation seconds per numerical tick at requested speeds 1, 10, 60, 150 or 300. A monotonic clock sets the target cursor; bounded batches catch up with at most twelve preparation calls or eight milliseconds between yields. Wall time changes scheduling only. Slow devices may run slower than the requested rate, with `playbackLagSec` reporting the current shortfall; they never skip numerical ticks.
- Complete frames are presented at most once per forty milliseconds (25 Hz), plus forced pause/end frames. Every intermediate tick's deliveries accompany the next frame in `observationBatch`, including that frame's own readings. The frontend replaces history from `observations` first, then merges the batch and frame readings by ID. Low hardware throughput can produce fewer than 25 frames per second without losing readings.
- Pause flushes all completed ticks before stopping scheduled work. Seek also pauses and rounds down to a five-second boundary within the computed frontier.
- The playback cursor and computed frontier are separate. Running from a rewound cursor replays deterministic existing history before extending the frontier.
- `load` restores the frontier from `scenario.authoritativeTimeSec`, emits a time-zero ready frame, and does not start a run. The UI then sends `seek` with the saved cursor. Persisting `SandboxDocument` must copy its `computedUntilSec` into `scenario.authoritativeTimeSec` before reloading.
- Each frame contains only readings delivered at that tick. Delayed observations retain their original observation time and distinct receipt time. Ready and the completed seek's paused event additionally contain regenerated reading-only history for an adaptive recent window **of receipt time** at the cursor. The accompanying seek frame does not retransmit it. A resumed run may send one replacement history if an interrupted seek invalidated its cached window. Routine run frames and pauses contain no full history.
- `historyStartSec` is authoritative. It is relative to `scenario.startTime` and equals `max(0, cursorSec - retainedWindowSec)`. The window derives from the 144,000-observation budget: one ordinary sensor gets 719,995 seconds (almost 200 hours), thirty get 23,995 seconds (6 hours 39 minutes 55 seconds), and 500 get 1,435 seconds (23 minutes 55 seconds). A conservative maximum deliveries-per-tick count accounts for distinct configured delays. The frontend filters/prunes by `receivedAt` between the reported start and displayed timestamp. It must not assume six hours or prune by source observation time.
- Receipt buckets with a head index support amortized incremental eviction, without scanning the retained map on each tick or frame. Unexpected excess fails explicitly instead of silently dropping readings. Replacement history is filtered only on load/seek/recovery. Seeking outside the retained window reconstructs the appropriate older window; it does not leak future readings or claim unlimited history.
- An exact packed-frame LRU retains at most 64 frames and 16 MiB of accounted storage. Terrain indices use `Uint32Array`; combustion values use `Float64Array`, preserving the checksum's numeric values and property ordering. The accounting includes actual typed-array bytes plus twice serialized metadata bytes; it is an estimate for metadata, not a browser/process RSS ceiling. Cached seeks still transfer the retained observation window. Uncached seeks use sensor checkpoints instead of retaining every 40,000-cell frame.
- Sensor checkpoints retain at most 15,360 sensor states, with a ceiling of 15,360 checkpoints and a floor of two, including permanent time zero. This gives 15,360 checkpoints for one sensor, 512 for thirty, and thirty for 500. A sorted time index locates the nearest checkpoint by binary search. A normal one-sensor 29-hour recording retains all 1,741 minute checkpoints and 20,881 readings. Eviction can make an old seek slower, but cannot change its result. `prepareFrame` rebuilds missing state in bounded five-second steps, including historical source states for delayed samples. Combustion is reconstructed analytically from first arrival plus immutable fuel parameters, so its mass and source fields are preserved on rewind without a mutable fuel-history array. Input, cursor and frontier suffice for IndexedDB persistence.

`apps/sandbox/src/runtime/controller.ts` implements the scheduler; `simulation.worker.ts` is its narrow worker adapter. No networking or database functionality is added by this runtime.

## Exact-output reconstruction optimization

Saved-frontier reconstruction uses the engine's internal `prepareReadings` API for hidden five-second ticks. It performs the same bounded sensor integration, delivery scheduling, quality flags and historical source-state preparation as `prepareFrame`, but omits terrain arrays and full-frame SHA-256 construction until a frame is actually displayed. The final frame still contains the complete combustion, burning/burned cells, weather and checksum. Normal Run frames also remain complete.

Local heat/smoke source values are evaluated lazily only where a sensor's existing spatial kernel requests them. The same `combustionAt` calculations and accumulation order are used; no footprint, threshold, propagation rate, physical parameter, noise sequence or numerical step changed. The eager `sourceFieldAt` reference remains available, and exact equality tests compare eager/lazy targets across calm and directional winds. These execution changes preserve engine 1.3.0 and its checkpoint compatibility.

This removes 4,320 undisplayed terrain-frame constructions/hashes in a normal six-hour restore after its time-zero ready frame, and avoids evaluating all 40,000 cells' local sources when one sensor only queries a small neighborhood. Cancellation remains between bounded integration batches. High-speed playback uses the same observation-only path between presentations; `renderFrame` materializes an already computed tick without repeating its historical delay integration. No physics or engine identity changes accompany these execution optimizations.

## Bounded terrain preparation for long durations

Directional rate integrals are computed lazily in six-hour numerical chunks, with five-second samples and exact weather knots. At most four condition windows and 128 rate tables are retained, independent of the number of declared hours. The first six-hour numerical grid retains the previous solver's ordering and fallback behavior. Beyond the final changing weather sample, a constant tail uses direct distance/rate travel time, so a very large requested horizon does not create a horizon-sized array or loop through the entire constant tail for each edge. Published nonlinear fuel fallback integration also switches to analytical constant-tail travel after the existing six-hour numerical region.

Chunking is a storage/execution change, not a new wind or fire-rate model. The later combustion/observation migration intentionally changes outputs and bumps the engine to 1.3.0; old 1.2.0 checkpoints are rejected. Current 1.3.0 frame checksums at 0, 30, 300 and 21,600 seconds are pinned in regression tests. Changing-weather chunk convergence is tested against half-sized time steps. A long declared run can initialize quickly, but computing exact sensor noise and responses at a distant cursor still requires all intervening five-second integration steps not covered by retained checkpoints. There is no claim of instantaneous arbitrary-duration replay.

## Historical wind direction and strength audit (before engine 1.2.0)

`npx tsx packages/simulation/src/wind-audit.ts` audits uniform terrain and the actual prepared Glendalough landscape. Wind directions are meteorological **from** bearings, clockwise from north. The engine converts them to transport components `east = -speed * sin(from)` and `north = -speed * cos(from)`. Cells run west to east within rows and south to north across rows. Thus wind from north transports south, and wind from west transports east. Both single-sample and time-interpolated solvers pass the eight-direction tests. Display polygons increase latitude with row index; the terrain raster reverses rows to match image coordinates. A screen arrow must additionally account for map bearing, or the map must remain north-up; the frontend owns that correction.

At five m/s over uniform flat grass, the 100 m cardinal downwind arrival was 120.49 seconds versus 488.61 seconds upwind in all four cardinal orientations. At 141.42 m along diagonals the corresponding arrivals were 170.40 and 690.99 seconds. No numerical direction inversion was reproduced, so this audit does not invert the physics or arbitrarily retune wind strength.

The current illustrative multiplier is `exp(clamp(0.35 * canopyAdjustment * alongEdgeWindMps, -1.5, 2))`, where canopy adjustment is 0.25 for woodland and 0.4 otherwise. It is already bounded between 0.223 and 7.389, with an additional final rate ceiling of eight m/s. For flat grass, head/back multipliers at five m/s are 2.014/0.497; at ten m/s, 4.055/0.247; at twenty m/s, 7.389/0.223. The response is monotonic until those explicit caps, and perpendicular wind does not directly accelerate an edge. These are declared empirical parameters, not a field-calibrated claim. A request to change strength needs a specified modeling objective rather than assuming that every observed non-downwind front is erroneous.

On actual terrain with controlled five m/s west wind, 200 m east reached at 953 seconds, west at 4,665, north at 933 and south at 6,894. Flattening elevation while preserving cover/fuels changed east to 1,156 and north to 1,934 seconds, demonstrating why the uphill north front can outrun the east front. Changing elevation affected 17,798 mutually reached cells; no water cell burned. The audit retains terrain barriers and does not claim that wind must dominate every slope or land-cover discontinuity.

The six-hour bound and direction audit do not change the physics or `ENGINE_VERSION`; existing thirty-minute checksums and checkpoint compatibility are retained. If a future calibration changes rates, it must increment the engine version and require an explicit new run/revision for existing saved results.

`npm run typecheck` passed for the complete workspace after the frontend entry point became available. Browser memory depends on engine and structured-clone overhead; the measured Node RSS includes the source loader and runtime and is not a browser memory budget. Initial terrain computation remains synchronous inside the worker. Heterogeneous custom published-fuel terrain may trigger slower reference integration, so the timing above applies to the prepared fixture. Cross-browser floating-point transcendental functions can differ in their least significant bits; SHA portability alone does not establish bitwise numerical equivalence between every JavaScript engine. This simulator remains an illustrative model, not a validated wildfire forecast.
